# 명령→관절 반응 지연 분해 (0930, 기존 기록만 사용 — 새 실물 조작 없음)

자료: candump_0929_1401.log (g11a 실물 14:02, stage8 스트리밍 전 구간) + rl_bridge_20260929_140230.jsonl (같은 시각).
분석 창: 정책 실행 5–45 s. 도구: can_lag.py (응답 프레임 = 같은 ID, data[0]=모터 ID, 명령 뒤 5 ms 이내).

| 구간 | 지연 (12 모터 전부) | 상관 |r| |
|---|---|---|
| 정책 raw → 브리지 목표 (슬루+LPF) | 40–100 ms | 0.3–0.8 (0929 21:01 로그) |
| **브리지 목표 → CAN 명령 프레임** | **200–220 ms** | 0.96–0.99 |
| CAN 명령 → 모터 응답 위치 | 40–60 ms | 0.90–1.00 |

| (합계) 브리지 목표 → 브리지 qpos | 320–340 ms | = 0922·0929 실측 16틱과 일치 |

## 측정 사실
- 시계에 무관한 값: 모터 구간 40–60 ms (CAN 기록 단독), 브리지 목표→브리지 qpos 320–340 ms (브리지 단독) → **소프트웨어 구간 합계 ≈ 270–290 ms 는 확실**.
  명령 쪽 200–220 / 피드백 쪽 40–60 의 나눔은 candump 와 브리지가 같은 젯슨 시계(CLOCK_REALTIME)라는 가정에 기댄다.
- 모터 자체(명령→응답 위치)는 40–60 ms 로 빠르고 진폭도 거의 다 따라간다(예: 힙 명령 p2p 54.5° → 응답 51.1°).
- 지연의 약 2/3 가 **브리지가 목표를 낸 뒤 stage8 이 CAN 에 싣기까지**의 소프트웨어 구간에 있다.

## 가설 (작성 당시, 미검증) → 아래 '원인 확정' 참조
200–220 ms ≈ 10–11 틱 ≈ stage8 명령 구독 큐 깊이 10 × 20 ms. 단일 스레드 rclpy 실행기가 제어 타이머(50 Hz, CAN 입출력)·
상태 타이머(100 Hz, 수 KB JSON)·명령 구독(50 Hz)을 한 줄로 처리하다 뒤처지면, 큐가 가득 찬 채 유지되어 항상 10개 늦은
명령을 처리하는 상태가 된다. 대안 가설: 실행기 과부하 자체(큐 깊이와 무관한 처리 지연), 상태 발행 경로의 적체.

## 검증안 (대조 실험, 모터 무관)
젯슨에서 stage8 을 CAN 쓰기 끈 상태로 띄우고, 송신 시각을 넣은 가짜 SET_JOINT_TARGETS 를 50 Hz 로 보내 수신 지연을 잰다.
(a) 현재 그대로 (b) 명령 구독 깊이 1 (c) 상태 타이머 100→20 Hz — 하나씩만 바꿔 비교. 지연이 (b)·(c)에서 사라지면 원인 확정.

## 함의
- 이 구간을 없애면 실물 루프 지연 ≈ 16 → 6틱(시뮬 지연 ~3틱 상당). G11a(3–8틱 학습)·G12(지연 6 시뮬 정지 150/192)의 학습 범위 안.
- 지금까지 '지연'을 시뮬에 넣어 정책이 견디게 하는 방향이었으나, 지연의 대부분은 고칠 수 있는 소프트웨어 적체일 가능성.
- 액추에이터 네트워크(아래 검토)는 이 적체를 먼저 없애거나 따로 모델링한 뒤에 학습해야 한다(부하에 따라 변하는 소프트웨어 지연을 모터 특성으로 잘못 학습).

# 액추에이터 네트워크 검토 (Hwangbo 2019 방식)
- 지원: Isaac Lab 에 ActuatorNetMLPCfg / ActuatorNetLSTMCfg 가 내장(isaaclab/actuators/actuator_net_cfg.py) — 학습한 네트워크 파일만 있으면 붙일 수 있다.
- 데이터: 브리지 블랙박스 54개(50 Hz, 목표·관절각·속도·전류 기반 토크 추정·IMU·접촉) + CAN 기록 2개(0929, 모터별 명령 위치·kp·kd, 응답 위치·속도·전류).
  모터 단위 학습 자료로는 CAN 기록이 정확(타임스탬프가 버스 기준). 단 50 Hz 라 원 논문(수백 Hz)보다 거칠다.
- 한계:
  1. 엔코더가 로터 쪽이라 **발목 유격(~8°)·무릎 탄성 처짐은 모터 자료에 안 보인다** — 모터 액추에이터 네트워크로는 학습 불가. 이 부분은 IMU·기구학으로 따로 식별해야 한다.
  2. 자료 대부분이 서 있는 자세 근처 — 넘어지는 큰 동작에서는 외삽이 된다.
  3. 소프트웨어 지연(위 200 ms)을 먼저 정리하지 않으면 그걸 모터 특성으로 학습한다.
- 권고 순서: ① 소프트웨어 적체 확인·제거(가장 싸고 효과 큼) → ② 모터 반응(40–60 ms)을 CAN 자료로 확인 → ③ 필요하면 액추에이터 네트워크, 발목 유격은 별도 모델.


# 원인 확정 (0930 16:00–16:12, 젯슨 가상 CAN 벤치 — 실물 버스·모터 미사용)

도구: jetson/bench/stage8_vcan/ (가상 can9 + 가짜 모터 12 + ROS_DOMAIN_ID 77). 50 Hz SET_JOINT_TARGETS 25 s.

| stage8 | 명령 처리 /s | CAN 명령 Hz | 발행→CAN 지연 |
|---|---|---|---|
| 원본 v0 (2회) | 31.9 / 31.7 | 32 | 200 / 205 ms |
| v1 명령 구독 깊이 1 | 23.8 | 36 | 30 ms |

- 실물 세션(0929 21:01)의 stage8 명령 처리율 31.1 /s 를 벤치 원본이 그대로 재현(31.7~31.9) → 벤치가 실물 병목을 재현.
- **상태 JSON 은 원인이 아니다**: 젯슨 순수 파이썬 직렬화 0.215 ms/회, v2 에서 처리율 변화 없음. (위 가설의 '상태 타이머 적체'는 기각)
- **원인 (cProfile, 34 s)**: `robot_runtime/dof12_mapping._require_joint → load_12dof_config → json.load` 가 관절 조회마다
  21 KB 하드웨어맵을 다시 읽고 파싱 — 25,271회(≈740 /s), 프로세스 시간의 62 %. 제어 틱 평균 18 ms, 명령 1건 11 ms → 20 ms 주기 초과
  → 실행기가 명령을 초당 ~31건만 처리 → 구독 큐(KEEP_LAST 10)가 늘 참 → 10 건 × 20 ms = 200 ms 지연 + 38 % 누락.
  (같은 비율 38 % 가 브리지 관측에서 '관절값 무변화 틱' 으로도 보였다 — 상태 발행도 같은 실행기에서 밀림.)
- 수정: 파일의 (inode, mtime_ns, size) 가 같으면 파싱 결과를 재사용. 파일이 바뀌면 다음 조회에서 다시 읽으므로 '디스크의 현재 맵'
  의미는 그대로. 공개 load_12dof_config·get_joint_config 는 깊은 사본(호출자 수정이 캐시를 오염시키지 않음). tests/test_dof12_mapping_cache.py.
- 깊이 1 은 채택하지 않음: 추가 이득 5~10 ms 뿐인데 같은 토픽의 STOP_ALL·ARM 등 제어 명령이 다음 목표 명령에 덮여 사라질 위험.
